# RFC 0001: Spec 1.0.0

- **Status:** Draft
- **Author:** @GeoBradDev, interim steward
- **Spec version affected:** 1.0.0 (the first version)
- **Change type:** Major (the first published version)
- **Discussion issue:** [openpickleball/rating-spec#4](https://github.com/openpickleball/rating-spec/issues/4)

## Summary

This RFC proposes the first official OPEN rating spec, version 1.0.0. It says that an OPEN rating is what the reference engine, `openpickleball-engine` 1.0.0, calculates when it runs parameter set `v1`. It also sets the rules every tool that shows an OPEN rating must follow, the rules for retuning parameters later, and how retunes map to spec version numbers.

What matters most for a reader:

- **The evidence is thin, and the limits come first.** The engine was evaluated on one club's closed pool: 1,601 doubles matches among 189 players. Parameter set `v1` showed no measurable gain in accuracy over the engine's placeholder defaults. The engine can be gamed in known ways, and it rates fixed partnerships poorly. See [Evidence](#evidence).
- **A rating gap is stated as a share of points, not a chance of winning.** Under `v1`, a team rating gap of 0.5 means the stronger team is expected to win about 76.0% of the points, and a gap of 1.0 about 90.9%.
- **Some rules of the standard are proposed here but not yet built.** They are marked below, with the issue that builds each one.
- **The board decides.** Only the seated governing board can approve this RFC. The steward drafts it and cannot approve it. The places that need a board decision are marked **Decision for the board**.

Approving this RFC does not by itself make any rating official. The spec file, its changelog entry, and its implementing engine version follow in a separate pull request, as [rfcs/README.md](README.md) describes.

## Motivation

No official version of the spec exists, so no OPEN rating can go live. The reference engine has reached 1.0.0, with a frozen public API and a published, fingerprinted parameter set, so a rating can now be named exactly and reproduced from the match ledger. This RFC writes down what spec 1.0.0 would be, so the public can comment on it and the board can vote on it once it is seated.

It affects:

- **Players**, whose OPEN rating would be calculated this way, and who need to know what a rating and its reliability mean.
- **Clubs, organizers, and platforms**, who would submit matches in one documented format and show ratings under the rules below.
- **Developers**, who need one exact reference to conform to.

## Evidence

### Limits first

Read these before anything else in this section.

- **One club, one closed pool.** The engine was evaluated on 1,601 doubles matches among 189 players from one club, from 2025-08-10 to 2026-11-20. All were side-out scoring, and none were singles or rally scoring ([PARAMETERS.md, Data](https://github.com/openpickleball/engine/blob/v1.0.0/PARAMETERS.md#data)). Nothing here shows how the method behaves in singles, in rally scoring, or across many clubs.
- **`v1` is not shown to predict better.** On held-out matches, `v1` showed no measurable gain in accuracy over the `Config()` defaults. The rule for changing the defaults was fixed before the run. It needed the lower bound of a 95% interval on the improvement to be above 0 on Brier score or on log loss. Neither was. `v1` did pass a non-inferiority bar on Brier score only (a lower bound above -0.005), so it is no worse on Brier within that margin, but it is not shown to be no worse on log loss ([PARAMETERS.md, Default-change rule and result](https://github.com/openpickleball/engine/blob/v1.0.0/PARAMETERS.md#default-change-rule-and-result)). `v1` is proposed because it declares what a rating gap means, not because it predicts better (see [The gap and level statements](#the-gap-and-level-statements)).
- **A test on later matches is still pending.** A test on matches played after the evaluation, registered in advance, is still pending ([engine README, Known limitations](https://github.com/openpickleball/engine/blob/v1.0.0/README.md#known-limitations)).
- **Known weaknesses.** The evaluation simulated leagues of invented players whose true skill was known. The engine README lists what it found ([Known limitations](https://github.com/openpickleball/engine/blob/v1.0.0/README.md#known-limitations)). In short:
  - **Regular partners end up with the same rating.** Two players who always play together get the same updates, so the engine cannot tell who is carrying whom, and reliability gives no warning.
  - **Losing on purpose is not detected.** A player who throws matches drops, stays low for a long time, and nothing flags it.
  - **Colluding accounts can inflate one player.** Made-up league matches count without limit. The repeat rule limits self-reported matches, but does not stop the gain.
  - **A closed group can be labeled established.** New players who play only each other stay near the starting rating whatever their skill, and can still be labeled established. The connectivity cap meant for this case is off in `v1`.
  - **`v1` makes gaming pay more** than the defaults, because it moves ratings faster: the sandbagging and collusion effects were 1.9 to 2.6 times as large.

  These findings show what the engine does in each situation, not how often it happens in real play. Each comes from 20 simulated runs of one fixed setup on a pre-1.0 build (0.3.0.dev0).
- **The rating math has a known gap at the bounds.** Clamping at 2.0 and 8.0 lets rating leak into or out of the pool ([engine#27](https://github.com/openpickleball/engine/issues/27), open). No match in the evaluation data touched the floor or the ceiling ([PARAMETERS.md, Data](https://github.com/openpickleball/engine/blob/v1.0.0/PARAMETERS.md#data)).

A rating is an OPEN rating under spec 1.0.0 only when it was produced by a full replay of the match ledger under this engine version and this parameter set, and the replay's `params_version` is `v1` and its parameter fingerprint is `f9149f3c38a01efc`. A label alone proves nothing: the fingerprint must match ([docs/parameters.md, Identity](https://github.com/openpickleball/engine/blob/v1.0.0/docs/parameters.md#identity)). Every shown rating carries `params_version` and the parameter fingerprint, and the tool that shows it names the engine version, taken from the installed package (`open_engine.__version__`), not from the config's own version field, which a caller can set to anything ([What a shown rating carries](https://github.com/openpickleball/engine/blob/v1.0.0/docs/parameters.md#what-a-shown-rating-carries)). So any rating can be checked and reproduced.

The engine's `Config()` defaults are not spec 1.0.0. `Config()` is not a published parameter set, and its scale is a placeholder that declares no meaning for a rating gap.

This is more exact than the repository README's current wording, which says each version records "the config version and config fingerprint". Since engine 1.0.0, the parameter set label and the parameter fingerprint name the values apart from the package version, and the engine version names the code. If this RFC is approved, the spec pull request should update the README's wording to match.

**Text and code.** [`docs/model.md`](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md) at the tag is the written method, and the engine at the tag is the reference implementation. Each equation in `docs/model.md` names the function that computes it. Proposed: if the two disagree, the disagreement is a defect, reported publicly and settled by a later spec version. Until it is settled, the engine's output at the tag is what was published, so published ratings stay reproducible.

### Inputs, equations, and reliability

By reference to [`docs/model.md`](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md) at the v1.0.0 tag. In plain language:

**Inputs.** A match has a unique match id, two teams (one player each in singles, two in doubles), the score of each game, the date it was played, the rating format (singles, overall doubles, or a doubles category), the match type (tournament, league, recreational verified, or self-reported), the game format (side-out or rally scoring, and points to win), best of N games, and how it ended. Only a completed match counts. A self-reported match needs a confirmation from a player on each team. The checks that stop a match from counting are listed in [When a match does not count](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#when-a-match-does-not-count).

**Starting rating.** Every player starts as a new player at 3.5 in singles and in overall doubles. Spec 1.0.0 does not seed players from external ratings, because the evaluation's seeding test did not pass ([What a rating means](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#what-a-rating-means)).

**The update.** A team's rating is the mean of its players' ratings ([Team rating](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#team-rating)). The ratings predict the share of all points team A should win ([Expected point share](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#expected-point-share)):

```text
x = clamp((R_B - R_A) / scale, -12, 12)
E = 1 / (1 + 10**x)
```

A match moves each player by how far the team's actual share of points was from `E` ([Match performance](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#match-performance)), times the match's evidence weight ([Evidence weight](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#evidence-weight)), times the player's own K, which is larger when the player's rating is less certain ([K](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#k), [The update](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#the-update)). So a team can win and still lose rating, when it wins by less than expected. Inactivity widens uncertainty but never moves a rating ([Inactivity](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#inactivity)). Ratings stay between 2.0 and 8.0.

**Reliability.** Reliability is a number from 0 to 100. It combines how certain the rating is with how many different partners and opponents the player has had in the last year ([Reliability](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#reliability)). It changes no rating. An imported reliability from another system is never converted and is shown separately.

**Win probability** is a prediction only. No rating reads it ([Win probability](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#win-probability)).

The model's assumptions, including that a team has no partner term, are in [Assumptions](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#assumptions) and [What the model does not do](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#what-the-model-does-not-do). The engine's fixed constants, which are not parameters, are listed under [Parameters](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#parameters) and are pinned by the engine version.

### The gap and level statements

**What a rating gap means.** Under `v1`, a team rating gap of 0.5 means the stronger team is expected to win about **76.0% of the points**, and a gap of 1.0 about **90.9% of the points** ([What a rating means](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#what-a-rating-means)). A gap of exactly 1.0, the scale, means the stronger team is expected to win 10 points for every 1 the other team wins.

This is a share of points, **not the chance of winning the match**. A small edge on every point adds up over a game, so the model predicts a chance of winning the match that is further from 50% than the point share. That prediction rests on assumptions that only approximate side-out scoring. It also depends on the game format, the number of games, and the win calibration. Do not read 76.0% as "wins 76% of matches".

This meaning is **declared**, not fitted: the scale in `v1` does not move when the data or a fit changes. Changing it takes a new parameter set with a new fingerprint, and under this RFC a new major spec version (see [How retunes map to spec versions](#how-retunes-map-to-spec-versions)).

**What the level means.** Every new player starts at 3.5. A rating places a player relative to the players they have played, directly or through others. It is not tied to any outside measure of skill. In singles or overall doubles, a pool where everyone starts new keeps its average near 3.5 whatever its players' skill, as long as the small gains and losses that do not cancel out between teams stay small. So ratings from two pools that share no players are not comparable: the same number can stand for a different level in each. Matches between players of the two pools link them.

No parameter is chosen to move OPEN ratings toward any external rating. An imported external rating is a seed only, never a conversion, and spec 1.0.0 uses none.

### The rules of the standard

These rules apply to every tool that shows an OPEN rating. Code applies them automatically, in the engine or the backend, except the first, which each displaying tool must follow. Some are built, and some are proposed here and not yet built. The board's conformance requirements, which will check tools against these rules, do not exist yet: the board writes them once it is seated.

| Rule | State | What implements it |
| --- | --- | --- |
| **Reliability is shown with every rating.** A tool that shows an OPEN rating shows its OPEN-earned reliability next to it. An imported reliability, if any, is shown separately and labeled as such. | The engine reports it with every rating. Showing it is a conformance requirement on each tool. | Engine 1.0.0: `PlayerSummary.reliability` and `PlayerSummary.imported_reliability`. Each displaying tool, checked under the board's conformance requirements. |
| **Reliability stays below 60 until a player has organizer-submitted matches.** While a player has fewer than 3 verified matches (tournament, league, or recreational verified) in a rating format, such as singles or overall doubles, displayed reliability in that format is capped below 60. Self-reported matches still count toward the rating and its reliability, but cannot make a rating credible alone. Ratings themselves do not change. | **Proposed, not yet implemented.** Engine 1.0.0 does not apply it: a player with only confirmed self-reported matches can show reliability above 60. | [engine#164](https://github.com/openpickleball/engine/issues/164) (open), as a declared `Config` field that is on by default. |
| **Every integration submits matches in one documented format.** The single endpoint, the bulk endpoint, and the CSV upload all map onto one published match schema and pass the same validation. | **Proposed, not yet implemented.** | [backend#80](https://github.com/openpickleball/backend/issues/80) (open), with its field reference published as part of the standard. |
| **Anomaly detection flags only and never penalizes.** Suspicious patterns raise a flag for moderators and organizers. A flag is a signal, not a finding. It never changes a rating automatically. | **Proposed, not yet implemented.** The engine applies no penalty. The backend flags are not built yet. | The backend: [backend#213](https://github.com/openpickleball/backend/issues/213) (flag feed for organizers) and [backend#40](https://github.com/openpickleball/backend/issues/40) (moderator admin), all open, with the detection issues they list. |

**Rules that need a human judgment call wait for governance.** Any rule that needs a person to decide about a specific player or match, such as a penalty, a ban, or an appeal, is not part of spec 1.0.0. The board sets those rules later, with an appeals process.

> **Decision for the board: the reliability rule and the reference.** Engine 1.0.0 does not implement the reliability rule in engine#164. Implementing it adds a `Config` field, and adding a field changes every parameter fingerprint, including `v1`'s ([A release that changes the Config payload](https://github.com/openpickleball/engine/blob/v1.0.0/docs/parameters.md#a-release-that-changes-the-config-payload)). How a published set carries across such a release is not decided yet (engine#48). So spec 1.0.0 cannot both name fingerprint `f9149f3c38a01efc` and require the rule through the engine. **Proposed:** spec 1.0.0 is not published until an engine release implements engine#164, and this RFC's reference is then updated to that release, its commit, and the parameter set label and fingerprint it publishes for the same values as `v1`. Whether that set keeps the label `v1` or gets a new one is not decided yet (engine#48). The alternative is to publish on engine 1.0.0 and treat the rule as a display requirement on each tool until the engine applies it. That puts the same rule in many places, so it is not recommended.

### The retune policy

The parameters will be retuned as data grows. This policy follows the engine's [docs/parameters.md](https://github.com/openpickleball/engine/blob/v1.0.0/docs/parameters.md) at the tag. A retune never changes a published parameter set. It publishes a new one with a new label, such as `v2`, and `v1` keeps its values ([A published set never changes](https://github.com/openpickleball/engine/blob/v1.0.0/docs/parameters.md#a-published-set-never-changes)).

- **A gate on held-out matches.** A new set needs a test on matches it was not tuned on, with the rule fixed before the run. Tuning and scoring on the same matches does not count ([Evidence each new set needs](https://github.com/openpickleball/engine/blob/v1.0.0/docs/parameters.md#evidence-each-new-set-needs)). Proposed for the spec: the gate compares the new set against the set in the current spec version, with the same kind of rule as the engine's default-change rule (bootstrap intervals on Brier score and log loss, a gain bar and a non-inferiority bar). Proposed: a retune must clear the gain bar, not only the non-inferiority bar, because moving every player's rating needs a shown gain in accuracy. **Decision for the board:** which bars a retune must clear. (`v1` itself cleared only the non-inferiority bar. It is proposed for 1.0.0 because it declares the meaning of a gap, and there is no earlier official set to compare it with.)
- **A published rating shift report.** Before a re-rate goes live, how ratings move by percentile is published: the old ratings against the new ones, on the same ledger ([Existing ratings when a set changes](https://github.com/openpickleball/engine/blob/v1.0.0/docs/parameters.md#existing-ratings-when-a-set-changes)).
- **Change caps.** Each parameter will have a stated limit on how far it may move in one retune, with a helper that checks a candidate set against the current one. **Neither the caps nor the helper exists yet.** They are planned in [engine#48](https://github.com/openpickleball/engine/issues/48) (open) ([Change caps](https://github.com/openpickleball/engine/blob/v1.0.0/docs/parameters.md#change-caps)).
- **Re-rating all history.** When a new set goes live, every rating is rebuilt by a full replay of the whole ledger under it. There is no mode that applies new parameters to future matches only, so every rating comes from one ledger and one parameter set ([Existing ratings when a set changes](https://github.com/openpickleball/engine/blob/v1.0.0/docs/parameters.md#existing-ratings-when-a-set-changes)).
- **The schedule.** Early on, parameters are retuned at data milestones, such as 5,000, 10,000, and 25,000 matches. Once they settle, every six months. A retune ships only when its gate passes ([Schedule](https://github.com/openpickleball/engine/blob/v1.0.0/docs/parameters.md#schedule)).

Every retune changes the official spec, so each one goes through an RFC and a board vote, as [GOVERNANCE.md](https://github.com/openpickleball/.github/blob/main/GOVERNANCE.md) requires. The RFC carries the gate result and the shift report as its evidence.

### How retunes map to spec versions

The repository README says any changed parameter is a major version. With scheduled retunes, every retune would then be a new major version: several in the first year or two, then two a year.

> **Decision for the board.** The board decides which rule to adopt. The steward proposes the one below.

**Proposed rule:**

- **Major:** anything that changes what a rating means or how it is calculated. That is a change to the equations or inputs, a change to any declared value (such as the scale, which sets what a gap means, the rating range, the starting rating, or the match weights), a change to a rule of the standard that moves ratings, or a retune that breaks a change cap.
- **Minor:** a scheduled retune that changes only values fitted on data (including a placeholder default that the retune fits for the first time), passes its gate, stays within every change cap, and leaves every declared value as it was. Also, as today, an addition that leaves existing ratings unchanged.
- **Patch:** as today, a wording fix with no effect on any rating.
- **Until change caps exist, every retune is major.** A minor retune depends on caps that are not written yet (engine#48).

Every version, of any kind, still names its engine version, parameter set label, and parameter fingerprint, and every retune still re-rates all history and publishes its shift report.

**Why:**

- **Major should mean "the meaning changed".** Players, clubs, and tools need to know when a 4.0 stops meaning what it meant. A retune of fitted values under the same declared scale keeps the meaning of a gap and of the level, so it should not look like the same kind of change as a new formula.
- **Frequent majors lose their signal.** If every scheduled retune is major, major versions become routine, and a real change of meaning looks like any other.
- **Reproducibility does not depend on the number.** Each version pins the exact engine and parameter fingerprint, so any rating can be reproduced whatever the version number says.
- **Caps make minor safe.** A retune that stays within published caps cannot move ratings far, and the shift report shows how far they did move.

The cost: a minor version can now move existing ratings, which the current README rules out. If the board adopts this rule, the spec pull request for 1.0.0 updates the README's Versions section to match.

## Effect on existing ratings

None. No OPEN rating has been published, so there is nothing to shift ([PARAMETERS.md, Shift summary](https://github.com/openpickleball/engine/blob/v1.0.0/PARAMETERS.md#shift-summary)).

When spec 1.0.0 goes live, the first official ratings come from a full replay of the ledger under it. Every player starts as a new player at 3.5, since spec 1.0.0 does not seed from external ratings. A player's first official rating may differ from any number an earlier demonstration showed them.

## Alternatives considered

- **Use the engine's `Config()` defaults instead of `v1`.** Neither predicts measurably better on the evaluation data. `Config()` declares no meaning for a rating gap, and its scale is an uncalibrated placeholder. `v1` declares one and records it in a fingerprinted set, so a change of meaning is always visible.
- **Wait for the pre-registered test on later matches before proposing 1.0.0.** Proposing now opens public comment early. The board can still wait for that result before it votes, and the steward recommends it does (see [Open questions](#open-questions)).
- **Keep "any changed parameter is major".** Simple and strict, but every scheduled retune becomes major (see [How retunes map to spec versions](#how-retunes-map-to-spec-versions)).
- **Version the spec apart from the parameter set**, so a retune changes only the parameter label and not the spec version. This gives two version numbers to show and check for every rating, and it moves retunes outside the spec's versioning, which governance uses to track changes. Not proposed.

## Open questions

1. **Lowering the 2.0 floor.** Should a later version spread ratings further apart, and lower the 2.0 floor to make room? Every player starts at 3.5, only 1.5 above the floor. A later version could spread ratings further from 3.5 (widen the rating unit) by declaring a larger scale with K to match. That changes no prediction while no rating reaches a bound ([What a rating means, Scale and K together](https://github.com/openpickleball/engine/blob/v1.0.0/docs/model.md#what-a-rating-means)). But the weakest players would then reach the 2.0 floor, and clamping there lets rating leak into or out of the pool ([engine#27](https://github.com/openpickleball/engine/issues/27)). Lowering the floor would make room. No match in the evaluation data touched the floor or the ceiling, but that data is one club. Lowering the floor is a statement about what the level means, and it would be decided without reference to any external rating. It would be a major version. **Decision for the board:** whether, when, and to what value.
2. **How retunes map to spec versions.** See the proposal above. **Decision for the board.**
3. **The reliability rule and the reference.** Whether spec 1.0.0 waits for an engine release that implements engine#164, which changes the reference fingerprint. See above. **Decision for the board.**
4. **Timing of the vote.** The steward recommends that the board not vote until the initial evaluation writeup is linked in this RFC and the pre-registered test on later matches has been run and reported. **Decision for the board.**
5. **Which bars a retune must clear.** Proposed: the gain bar, not only the non-inferiority bar. See [The retune policy](#the-retune-policy). **Decision for the board.**
